## 概要

Epic Games は本規約を必須（mandatory）として運用している。根拠として「ソフトウェアの生涯コストの80%はメンテナンスに費やされる」ことを挙げ、可読性・新規コードの即時理解・コンパイラ間互換性を目的とする。クラスは読み手のために整理し、public インターフェースを先に、private 実装を後に宣言する。公開ソースファイルは `// Copyright Epic Games, Inc. All Rights Reserved.` で始める必要がある。

## 命名規則

**PascalCase**: 先頭大文字・アンダースコアなし（例: `Health`, `UPrimitiveComponent`）。

**型プレフィックス一覧**:

| プレフィックス | 対象 | 例 |
|---|---|---|
| `T` | テンプレート | `TArray` |
| `U` | UObject 派生クラス | — |
| `A` | AActor 派生クラス | — |
| `S` | SWidget 派生クラス | — |
| `I` | 抽象インターフェース | — |
| `C` | concept-alike な struct | — |
| `E` | enum | — |
| `b` | boolean | — |
| `F` | それ以外のほとんどのクラス | — |

**メソッド命名**: 動詞を使う。真偽を返す関数は Yes/No で答えられる問いかけの形にする。

**マクロ命名**: 完全大文字＋アンダースコア区切り、`UE_` プレフィックス。マクロは namespace 内に置けないため、この `UE_` プレフィックスで代替する。

## モダンC++の方針

- **C++20 が最低要件**。`static_assert`、`override`、`final`、`nullptr` を使う。
- **`auto` は避ける**。例外はラムダのバインド・冗長なイテレータ・複雑なテンプレート式の場合のみ。
- **range-based for ループ**を従来のイテレータより優先する。
- **ラムダは許容**されるが簡潔にすべき。`[&]` や `[=]` の包括キャプチャではなく明示的なキャプチャを使う。
- **強く型付けされた enum**: 基底型を指定した `enum class` を使う。
- **move semantics**: コンテナ側でサポートされている。明示的に呼ぶ場合は `MoveTemp` を使う。
- **デフォルトメンバ初期化子**: 単純な値には有用だが、リビルドへの影響を考慮する。

**const の扱い**（コメント指針と併記されている項目）:
- 変更しない引数は const 参照／const ポインタで渡す
- 変更を行わないメソッドには const を付ける
- コンテナを変更しないループでは const を使う
- 戻り値を const にしない（move semantics を阻害するため）

**移植性のための明示サイズ型**: `bool`, `TCHAR`, `uint8`, `int8`, `uint16`, `int16`, `uint32`, `int32`, `uint64`, `int64`, `float`, `double`, `PTRINT` をプラットフォーム間の一貫性のために使う。

**標準ライブラリ利用**: 優れた結果を出し API の一貫性を保てる場合は標準ライブラリ機能を優先する。`<atomic>`, `<type_traits>`, `<initializer_list>`, `<regex>`（エディタ専用）, `<limits>`, `<cmath>`, `<cstring>` の関数は許容される。相互運用しないコードでは標準コンテナ（`std::vector` 等）は避ける。

## フォーマット規約

- **波括弧**: 常に新しい行に置く。単一文のブロックでも常に波括弧を含める。
- **インデント**: タブを使う（4文字相当）。スペースは使わない。
- **switch文**: `break` を入れるか「フォールスルーする」旨のコメントを入れる。常に default ケースを含める。
- **if-else**: 常に波括弧を使う。多岐分岐は一貫したインデントにする。

**namespace**:
- 大半の UE コードはグローバル namespace を避ける。新規 API は `UE::` namespace を使うべき。
- 実装詳細は `UE::*::Private::` に置く。
- グローバルスコープでの `using` 宣言は避ける（unity build に影響するため）。
- 型は適切な namespace 内で前方宣言する。
- マクロは namespace に置けない。`UE_` プレフィックスで代替する。

**物理的依存関係**:
- ファイル名のプレフィックスは最小限にする（例: `UScene.cpp` ではなく `Scene.cpp`）
- ヘッダガードには `#pragma once` を使う
- インクルードよりも前方宣言を優先する
- `Core.h` のような広範なヘッダではなく、具体的なヘッダをインクルードする
- モジュールの可視性のため Public / Private ソースディレクトリを分離する

**一般的なスタイル項目**:
- 依存の距離を最小化する
- 大きなメソッドはサブメソッドに分割する
- 関数名と括弧の間にスペースを入れない
- コンパイラ警告に対処する
- 文字列リテラルには常に `TEXT()` マクロを使う
- 変数のシャドーイングを避ける
- 無名リテラルではなく名前付き定数を使う
- 非振る舞い的な変更（挙動を変えない書き換え）を広範に行うことを避ける

## API設計指針

- **bool引数を避ける**。代わりに enum フラグを使う。
- パラメータリストは妥当な数に抑える。多数の値が必要な場合は struct パラメータを使う。
- `bool` や `FString` によるオーバーロードを避ける。
- インターフェースクラスは抽象でなければならない。
- `virtual` と `override` は併記して使う。
- UObject はポインタで渡す。参照では渡さない。

**カプセル化**: メンバは public/protected インターフェースの一部でない限り private にする。派生させないクラスには `final` を使う。protected のみのフィールドにはアクセサを用意する。

**プラットフォーム固有コード**: プラットフォームコードは適切に命名されたサブディレクトリに置く。プラットフォームの詳細はハードウェア抽象化レイヤー関数を通して抽象化する。コードベース中に散らばる `PLATFORM_*` チェックの代わりに `#define` ディレクティブでプラットフォーム特性を扱う。

## インクルーシブな用語選択

原文は「敬意ある言葉遣い（respectful language）」を明示的な方針として掲げている。

**避けるべきもの**:
- ステレオタイプを助長する比喩（例: "blacklist/whitelist"）
- 歴史的トラウマへの言及（"slave"、"master"、"nuke"）
- 俗語・口語表現

**代替方針**:
- 人については性別中立な代名詞（"they/them"）、ソフトウェアについては "it/its" を使う
- "whitelist" ではなく "allow list"
- "master" ではなく "primary"
- "slave" ではなく "replica"

## SCRAP BLITZ に活かせる部分

本プロジェクトは UE5.8 + C++（`Source/ScrapBlitz/Private/` 配下）で実装済み。この規約は今後の新規実装・既存コードレビュー時の**チェックリスト**として使える。以下は「原文のどの項目に対応する既存コードの状態を確認すべきか」の一覧であり、現状の実コードが準拠しているかどうかは未調査（このノート作成時点でコード側を読んでいない）。レビュー時に照合すべき項目として提示する。

**命名規則の照合ポイント**:
- [ ] クラスの型プレフィックスが一貫しているか（`U`=UObject派生, `A`=AActor派生, `F`=それ以外, `E`=enum, `b`=bool メンバ）
- [ ] boolean 関数名が Yes/No で答えられる問い方になっているか（例: `IsAlive()`, `HasTarget()` の形か）
- [ ] 自作マクロが `UE_` プレフィックス＋全大文字＋アンダースコア区切りになっているか

**モダンC++の照合ポイント**:
- [ ] `auto` の使用箇所がラムダ・冗長イテレータ・複雑テンプレート式の例外条件に収まっているか、それとも濫用されていないか
- [ ] enum が `enum class`（基底型指定）になっているか、生の `enum` が残っていないか
- [ ] ラムダのキャプチャが `[&]` / `[=]` の包括キャプチャになっていないか（明示キャプチャが原則）
- [ ] 変更しない引数が const 参照／const ポインタで渡されているか
- [ ] 非変更メソッドに `const` が付いているか
- [ ] 戻り値を const にしてしまっていないか（move semantics 阻害）

**フォーマットの照合ポイント**:
- [ ] 波括弧が新しい行に置かれ、単一文ブロックにも省略なく付いているか
- [ ] インデントがタブ（スペースではない）になっているか
- [ ] switch 文に `break` またはフォールスルー明記コメントがあり、default ケースが存在するか
- [ ] 文字列リテラルに `TEXT()` が漏れなく使われているか
- [ ] 変数シャドーイングが発生していないか

**API設計の照合ポイント（OC/SP技の新規実装時に特に有効）**:
- [ ] 関数シグネチャに bool 引数が並んでいないか（例: `DoAttack(bool bIsCharged, bool bIsAerial)` のような形は enum フラグ化を検討）
- [ ] パラメータ数が多い関数は struct 引数化されているか（技のパラメータが多い SP/OC 系実装で特に該当しやすい）
- [ ] `bool` や `FString` によるオーバーロードがないか
- [ ] インターフェースクラス（`I` プレフィックス）が抽象のままになっているか
- [ ] `virtual` 関数のオーバーライドに `override` キーワードが付いているか
- [ ] UObject の受け渡しがポインタになっているか（参照になっていないか）

**インクルーシブ用語の照合ポイント**:
- [ ] 変数名・関数名・コメントに "blacklist/whitelist"、"master/slave"、"nuke" 等の該当語が残っていないか（"allow list"、"primary/replica" 等への置き換え候補）

**namespace/物理依存の照合ポイント**（新規モジュール追加時）:
- [ ] 新規 API を追加する際、グローバル namespace ではなく `UE::` 系 namespace を検討したか
- [ ] ヘッダに `#pragma once` があるか、`Core.h` のような広範ヘッダではなく具体ヘッダをインクルードしているか
