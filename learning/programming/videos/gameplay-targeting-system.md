## Targeting System とは（GASとの関係・独立利用可否）

Gameplay Targeting System は、データ駆動型のターゲティングリクエストを作成するためのフレームワーク。原文は「Gameplay Ability System プラグインを拡張している」と明記しつつ、「独立して使用することも可能」ともしている。つまり GAS 専属の仕組みではなく、GAS を使わないプロジェクトでもターゲティング機能単体で導入できる設計になっている（原文がこの2点以上を掘り下げていないため、独立利用時の具体的な制約・セットアップ手順は本ソースからは不明）。

## Targeting Preset の構造

Targeting Preset はデータアセットであり、「複数の Targeting Tasks を上から順に実行する」という設定を定義する。原文で強調されている特徴は次の2点:

- 各タスクは**インラインプロパティ編集**をサポートする
- これにより、タスクごとに別々の UAsset を作らなくても、再利用可能なタスクとプリセットを構築できる

つまり Preset 自体は「タスクの実行順序リスト＋各タスクのパラメータ」という薄いコンテナで、タスクの実体は差し替え可能な部品として設計されている、と読める（データアセット化のメリットについての一般的な理由付けは原文になし）。

## Targeting Task の3分類（Selection/Filtering/Sorting）

原文が明示する3分類:

1. **Selection（選択）** — ターゲット候補を選出する
2. **Filtering（フィルタリング）** — 条件に基づいて絞り込む
3. **Sorting（ソート）** — 優先順位を設定する

Preset はこれらのタスクを上から順に実行するため、素直に読めば「まず Selection で候補プールを作り、Filtering で条件外を除外し、Sorting で優先順位を付ける」というパイプライン構成になる（この実行順序の解釈は原文の「複数の Targeting Tasks を上から順に実行する」という記述からの素直な読み取りであり、3分類が必ずこの順番で並ぶという明言そのものは原文中にはない）。

タスクは Blueprint 対応で、実装方式には「クラスデフォルトプロパティの設定」から「Blueprint callable events」まで幅がある、とだけ原文は述べている。各方式の具体的な使い分け基準は本ソースには記載がない。

## 同期/非同期の実行モデル

2種類の実行モデルが提供される。

### 同期実行（Immediate Targeting Requests）
`UTargetingSubsystem::ExecuteTargetingRequest` 関数で実行する。ゲームスレッドをブロックして即座に完了する。

### 非同期実行（Async Targeting Requests）
`UTargetingSubsystem::StartAsyncTargetingRequest` 関数で実行する。サーバー認証待機やゲームプレイイベント待機など、時間のかかる処理に対応できる。

原文は「全プラグイン提供タスクは両モデルをサポートしており、ゲームコードの必要性に応じて実装できる」としている。つまり同じタスクを同期・非同期どちらの経路からも呼び出せる前提で設計されている（同期/非同期をどう使い分けるべきかの具体的なガイドラインは原文になく、「即座に結果が要る場面」対「待機を伴う場面」という区分自体からの推測に留まる）。

## SCRAP BLITZ に活かせる部分

前提として、本プロジェクトには既に自作のマルチロックミサイルシステム（`project_scrapblitz_multilock`）と comboTarget 矢印 HUD（`project_scrapblitz_target_hud`）が存在する。以下は**既存実装を置き換えるべきという結論ではなく**、Targeting System の概念枠組みを使って既存ロジックを整理し直すとどう見えるか、という比較検討のための整理に留める。既存コードの実装詳細（該当関数・ファイル）は今回読んでいないため、対応関係は概念レベルの一般論として書く。

- **Selection/Filtering/Sorting という3分類の切り口自体は、複数敵からロック対象を選ぶロジックの整理に転用しやすい一般的なフレームワーク**。マルチロック構想の「レンジ内の敵を時間経過で順次ロックする」という蓄積方式は、素直に対応させるなら「レンジ内候補を集める＝Selection」「ロック済み・対象外種別などを除く＝Filtering」「どの順でロックしていくか・上限に達した時に何を優先するか＝Sorting」という3段に分解して捉え直せる、という一般的な見立てができる
- **単一ロック（comboTarget）と複数ロック（マルチロック）を同じ3分類の語彙で説明できる可能性がある**。単一ロックは「Selection→Filtering→Sorting の結果、上位1件だけを採用する」特殊ケースと捉えられ、マルチロックは「上位N件を採用する」一般形と捉えられる、という整理の仕方は概念上あり得る（あくまで捉え方の話であり、実装をこの形に揃えるべきという主張ではない）
- **同期/非同期という区分の考え方**は、マルチロックの「チャージ蓄積中に敵の生死・退場が起きた場合の再評価」のような、時間経過を伴う判定が既存実装にどう組み込まれているかを見直す際の一般的な観点になり得る。ただし既存実装が実際にフレーム単位の同期処理なのか、何らかの待機を挟んでいるのかは未確認であり、この観点が実際に当てはまるかどうかは別途コードを読まないと判断できない
- **HUD（homingArrow）の generalize 方針との関係**: `project_scrapblitz_target_hud.md` には「マルチロック対応時にプール化して複数表示に generalize 予定」とある。Targeting System 側は視覚表現（HUD）についての記述が原文に一切ないため、この観点では参照材料にならない。HUD の generalize は既存の設計方針のまま進めればよく、今回のソースから追加で得られる示唆はない

総じて、Targeting System は「候補選出→絞り込み→優先順位付け」という一般的なターゲティング設計の語彙を提供するもので、既存のマルチロック実装がこの語彙とどれだけ整合しているか（あるいは整合していないが別の理由で妥当か）は、実コードを読んだ上で改めて評価する必要がある。
