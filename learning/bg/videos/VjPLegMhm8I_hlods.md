## 全体構成（3 本柱）[00:15–00:39]

1. Instanced Static Meshes で描画を効率化
2. Hierarchical Level of Detail（HLOD）で遠景オブジェクトの複雑さを削減
3. Foliage の draw distance 設定で「見えているものだけ描く」

## 1. Draw Call の基礎とその削減 [00:40–04:33]

### Draw Call とは何か [01:10–01:21]
- **同じジオメトリ×同じマテリアルの組み合わせ = 1 Draw Call** という定義 [01:13–01:17]
- 例え話：フェンスの板を1色で塗る方が、板ごとに違う色で塗るより速い。GPU は「同じことの繰り返し」が得意で、「違うことを次々」は時間がかかる [00:53–01:10]
- 具体例：茅葺き屋根のメッシュは 2 マテリアルスロット（樽材のマテリアル＋支柱材のマテリアル）を持つため、それだけで 2 Draw Call を要する、という最小単位の説明 [01:25–01:34]
- 同じジオメトリ・同じマテリアルの茅葺きメッシュが複数あっても、画面内のどれが見えているかを個別に扱う必要があるため、**自動的には単一 Draw Call として扱われるわけではない** [01:37–01:47]（＝カリングとインスタンス化のトレードオフ [01:50–01:55]）

### Dynamic Instancing（UE 4.22 で追加）[01:50–02:42]
- 近傍にある 2 つ以上の Actor が同じジオメトリ・同じマテリアルを共有していれば、自動検出して 1 Draw Call として描画する機能 [02:00–02:04]
- 検証手順（そのまま転用可能）[02:09–02:41]:
  1. コンソールコマンド **`Stat RHI`** を実行 → `DrawPrimitive calls` の数値を確認 [02:09–02:19]
  2. **`r.MeshDrawCommands.DynamicInstancing 0`** で無効化 → `DrawPrimitive calls` が増加するのを確認 [02:22–02:34]
  3. **`r.MeshDrawCommands.DynamicInstancing 1`** で再度有効化 [02:34–02:38]
- 限界 [02:42–02:57]：Static Mesh の LOD 差・メッシュ間の距離など諸条件により、同ジオメトリ・同マテリアルの全使用箇所を必ずしもバッチ化できるわけではない

### Instanced Static Mesh Component + Merge Actors [02:57–04:33]
- 編集自由度（アーティストが個別に配置・調整できる）を保ったまま Draw Call を削減する狙いで、**Instanced Static Mesh Components** を使う。GPU に「これらは一括描画してよい」ヒントを与える仕組みで、各インスタンスセットが実質 1 Draw Call になる [03:07–03:16]
- 具体的な操作手順 [03:16–03:43]:
  1. 家ごとに茅葺きの見た目が確定した後、**同じ家の茅葺き Actor を全選択**
  2. 右クリック → **Merge Actors**
  3. 右側のオプションから「選択 Actor からジオメトリを収集し、Instanced Static Mesh Component へ統合するモード」を選択
  4. 結果は**1つの Actor**（内部は複数の Instanced Static Mesh Component で構成）にまとまる [03:19–03:25]
- **Keep Original Actors As Editor Only** を選択した理由 [03:43–03:55]：プロジェクト終盤の作業だったため、後で茅葺きを変更する必要が出た場合に備え、元 Actor を「エディタ上にのみ存在し、実行時には一切描画されない」形で残す。保険を残しつつ本番描画からは完全に除外
- 適用条件の見極め [03:57–04:22]：**限られた種類の Static Mesh が、同じ場所にまとまって大量にある**ケースで特に有効。茅葺き屋根はこの条件に合致したため採用。**風車の羽根**（複数の木製シングルをキットバッシュしたもの）も同条件に当てはまる例として言及 [04:27–04:32]（＝実際に適用したかは transcript からは不明。適用候補としての言及）
- 汎用的な適用場面 [04:15–04:24]：複数の Static Mesh を単一の Static Mesh Actor へ統合し、**追加の Static Mesh アセットとしてのメモリオーバーヘッドを避けたい**場合にも有効、という一般化した言及

## 2. Quad Overdraw とサブピクセル三角形 [04:37–06:14]

HLOD の必要性を導く「前提の理屈」として説明される区間。GPU が同じピクセルを複数回描画してしまう別パターン。

- GPU が同じピクセルを繰り返し描く 2 つの原因 [04:37–05:35]:
  1. **半透明の重なり**（例：フォグカードを何枚も重ねる）→ 各フォグ平面が同じピクセルを何度も計算する [04:48–04:59]
  2. **三角形のエッジのラスタライズ**：ベクター情報をラスタライズする過程で、**三角形が 4 ピクセルより小さい場合でも 4 ピクセル分の領域として描画されてしまう** [05:28–05:42]。遠くにある高詳細ジオメトリで頻発する現象 [05:44–05:46]
- 可視化手順：**View Modes → Optimization View Modes → Quad Overdraw** [05:02–05:07]。色が同じピクセルの描画回数に対応する [05:08–05:10]
- 実例（このプロジェクトのシーンで）[05:11–05:26]:
  - フォグの重なり箇所：**10 回以上**同一ピクセルを描画
  - フォグを隠した状態でも、中央に見える緑帯部分は**約 4 回**描画されている（＝非効率）
- 結論：**サブピクセル三角形は Quad Overdraw を引き起こすため悪** [06:00–06:04]

### 改善策 1: LOD（Level of Detail）[06:00–06:26]
- メッシュに LOD を用意し、カメラから遠ざかるほどジオメトリの複雑さを下げることで Quad Overdraw とサブピクセル三角形を緩和 [06:04–06:14]
- 本プロジェクトでは **Unreal Engine 内蔵の自動 LOD 生成ツール**を使用。「とても簡単で苦労がなかった」と明言 [06:14–06:23]（＝具体的な生成パラメータへの言及はなし）

## 3. HLOD（Hierarchical Level of Detail）本題 [06:26–09:53]

### なぜ HLOD が必要か [06:26–06:56]
- 疑問の提示：最終 LOD がさらに遠くなったらどうするか？その三角形はさらに画面上で小さくなり Quad Overdraw を招くのでは？→ **Yes、それで OK** という前置き [06:26–06:36]
- 単純に **Actor の Max Draw Distance を設定して描画自体をやめる**選択肢もあるが、**家のような大型オブジェクトにはこの手法は使えない**（完全に消えると不自然なため）[06:39–06:46]
- では最終 LOD を超えてさらに簡略化したものを描画したい場合はどうするか、という問いへの答えが **HLOD** [06:46–06:55]

### HLOD の定義 [06:56–07:10]
- 一群のオブジェクトを代表する、**さらに簡略化されたメッシュ**を作るシステム。「遠方から見るためのプロキシ（代役）メッシュ」[06:59–07:04]
- オブジェクトのクラスタを自動生成し、各クラスタに対応するプロキシメッシュも自動生成できる [07:04–07:10]

### HLOD の設定・生成手順（正確な操作列）[07:12–09:34]

1. **HLOD Outliner を開く**：メニュー `Window → HLOD Outliner` [07:12–07:22]
2. **レベルごとに HLOD を有効化する必要がある**（HLOD を使いたい各レベルで個別設定が必須）[07:23–07:29]:
   - 該当レベルの **World Settings → LODSystem グループ → `Enable Hierarchical Level of Detail System` チェックボックス** をオン [07:29–07:37]
   - 有効化が必要な範囲：**Persistent Level**、**Geometry サブレベル**、**各 House サブレベル**、**Foliage** まで含む全サブレベル [07:45–07:59]
   - Cluster Generation / Mesh Generation の設定値は**デフォルトのまま使用**したが、「各自のニーズに合わせてチューニングすることを強く推奨する」との明言 [07:37–07:45]（＝具体的なパラメータ数値への言及なし）
3. **House サブレベル固有の最適化**：各 House サブレベルで HLOD を有効化する際、HLOD Outliner で **`Generate Single Cluster For Level`** をチェック [07:59–08:09]
   - 理由：家丸ごとが 1 つの隣接エリアに収まっているため、**時間のかかる Cluster Generation プロセスをスキップ**でき、家全体を代表する HLOD が 1 つだけで済むと最初から分かっている [08:09–08:20]
   - この手法が使えたのは「各家を個別のサブレベルとして構築していた」という設計上のメリットによる、との言及 [08:20–08:24]
4. **Build 実行**：メインレベルに戻り、HLOD Outliner の**大きな赤い Build ボタン**を押す [08:24–08:35]
   - 処理内容：シーン内の全ジオメトリをループしてクラスタへグループ化 → 各クラスタのプロキシメッシュを生成 [08:35–08:44]
   - **時間がかかる処理**である旨の明言（「sit back and relax」）[08:46–08:50]
5. **生成結果の確認**：HLOD Outliner で個々の HLOD Actor を展開すると、クラスタに含まれる Actor 一覧・ズーム・クラスタサイズの確認ができる [08:51–09:12]

### HLOD の再生成（メンテナンス）[09:12–09:34]
- プロキシメッシュは自動生成物のため、**レベルに変更を加えるたびに更新が必要** [09:12–09:16]
- ライティングの Rebuild 要求と同様、**ビューポート左上に「HLOD クラスタの Rebuild が必要」という警告が表示される**仕組み。エンジン側がレベルへの変更を検知して知らせてくれる [09:18–09:28]
- 個別クラスタの再生成：該当クラスタを**右クリック → `Rebuild Proxy Mesh`** [09:28–09:34]

## 4. Foliage の Draw Distance（HLOD ではカバーされない領域）[09:34–11:21]

- 前提：**Foliage Tool でペイントしたフォリッジ・インスタンスは HLOD 生成の対象に含まれない** [09:36–09:43]
- 対策：Static Mesh Actor と同様に **Max Draw Distance** を設定し、一定距離より遠い小型メッシュは描画自体をやめる [09:44–09:53]

### 操作手順（Bulk Edit via Property Matrix）[09:53–10:26]
1. Content Browser で **Foliage でフィルタ** [10:00–10:04]
2. 全選択 → 右クリック → **Asset Actions → Bulk Edit via Property Matrix** [10:05–10:10]
3. 表示するプロパティを選択：**Instance Settings → Cull Distances → Min, Max** [10:16–10:21]
4. 各プロパティにカーソルを合わせ、ピンアイコンをクリックしてカラム表示に追加 [10:21–10:26]

### Min/Max の意味と運用方針 [10:29–11:21]
- **Min 距離でフェード開始 → Max 距離で完全にフェードアウトし、描画されなくなる** [10:29–10:34]
- フェードが不要ならば Max のみ設定すれば、その距離で瞬時に非表示になる [10:34–10:38]
- 値の決め方は**フォリッジのサイズに応じる** [10:42–10:44]:
  - 例：**broken pine tree assembly**（比較的大型）→ かなり遠くまで見えるように値を設定 [10:44–10:47]
  - 実践的なコツ：カメラを対象メッシュから遠ざけ、見た目を見ながら値を調整する [10:55–10:58]
  - **Spruce** という名前を含むアセットは大型の木でマップの反対側からでも見えるべきもの、という個別の判断基準の例 [11:01–11:07]（＝逆に値を大きく取り、遠くの木立がスカスカにならないようにする）
  - 逆に小型フォリッジ（例：**carrot**）は非常に低い値に設定。「マップの反対側からニンジンが見える必要はない」という明快な判断基準 [11:12–11:18]
- 実際に設定した全フォリッジタイプの cull distance 一覧は **Unreal Engine Marketplace 上のプロジェクトで確認可能**、という参照先の案内あり [11:21–11:26]（＝具体的な全数値は動画内では列挙されない）

## まとめ（動画終盤の総括）[11:27–11:38]

Draw Call 数の削減・描画対象そのものの削減・描画するものの複雑さの削減、という 3 つの切り口でパフォーマンスを改善する話だった、という締め [11:32–11:37]

## SCRAP BLITZ に活かせる部分

`L_Stage01`（廃工場・廃滑走路ヤード）の Content 肥大とドローコール課題に直接効く回。前作ノート（[uJVguudLrmw_performance-optimization.md](uJVguudLrmw_performance-optimization.md)）が「計測と意思決定プロセス」だったのに対し、本作は「具体的な削減の手」が主役。

1. **HLOD をサブレベル単位で仕込む発想** [07:23–08:24]：本プロジェクトは UE 移行後にレベル構成をどう区切るか（家＝サブレベル、のような単位分割）を検討する余地がある。動画の教訓は「1 つの隣接エリアで完結するオブジェクト群は個別サブレベル化しておくと、`Generate Single Cluster For Level` でクラスタ生成そのものをスキップできる」[08:09–08:20] という点。廃工場の建屋・滑走路脇の廃機体クラスターなど、**まとまりのある構造物をサブレベル単位で括っておく**設計が、後の HLOD 導入コストを下げる
2. **Instanced Static Mesh + Merge Actors（Keep Original Actors As Editor Only）** [02:57–03:55]：L_Stage01 で「同じ廃材メッシュを密集配置している箇所」（配管の集積・瓦礫の山・パレット/コンテナの積み上げ等）があれば、見た目が確定した後にこの操作で Draw Call をまとめられる。**元 Actor をエディタ専用として残す**運用は、まだ調整の余地がある終盤前の背景制作段階でも安全に試せる（本番描画には影響せず、いつでも戻せる）
3. **Quad Overdraw の可視化手順は今すぐ使える診断ツール** [05:02–05:26]：`View Modes → Optimization View Modes → Quad Overdraw` は特別な設定なしにそのまま L_Stage01 で確認できる。特に**半透明の重なり**（延焼エフェクト・スモーク・フォグ演出等、SCRAP BLITZ でも多用する要素）は本動画の指摘通り Quad Overdraw の主要因になり得るため、VFX 密度を上げる前に一度確認する価値がある
4. **Foliage Cull Distance の判断基準がそのまま使える** [10:42–11:18]：「大型オブジェクトは遠くまで見せる／小型は近距離のみ」という判断軸（Spruce vs carrot の対比）は、L_Stage01 の瓦礫・雑草・小物散乱物にそのまま適用できる考え方。**Bulk Edit via Property Matrix でフォリッジ種別ごとに一括設定**する手順も、地道な作業の効率化として直接転用可能
5. **HLOD 自体が「開発時は詳細・遠景は自動簡略化」を仕組み化する手段** [06:56–07:10]：既存ドクトリン §9「映る範囲だけ品質を上げる」の実装手段が、これまで（Foliage ForceLOD・billboard 等）は「作業者が距離ごとに手動で判断する」ものだったのに対し、HLOD は**クラスタ化とプロキシメッシュ生成をエンジン側に任せる自動化**である点が質的に異なる。UE 移行後、L_Stage01 のような大規模ステージでは HLOD 導入を検討する価値がある
6. **HLOD は変更のたびに Rebuild が要る点に注意** [09:12–09:28]：ライティング Rebuild と同種の「メンテナンスコスト」が発生する仕組みなので、背景の物量調整が頻繁な制作中盤ではなく、**レイアウトがある程度固まった段階で導入するのが合理的**（ビューポート左上の警告表示で検知は自動化されている）

※ 本動画では Cluster Generation / Mesh Generation の詳細パラメータ数値、Foliage cull distance の具体的な数値一覧には踏み込まれない（「デフォルトのまま使った」「詳細は Marketplace のプロジェクトを見てほしい」との案内のみ）。数値のチューニングが必要になった際は UE 公式ドキュメントか実プロジェクトファイルでの確認が必要。
