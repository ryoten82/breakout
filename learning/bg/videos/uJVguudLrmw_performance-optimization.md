## この動画の主眼：FPS でなく milliseconds で考える理由 [00:39–01:10]

- FPS は指標として直感的だが**非線形**。ミリ秒（frame time）は**線形**なので改善量の比較に向く
- 具体例 [00:56–01:10]: 25→30 FPS の改善に必要な frame time 短縮は **7ms**。一方 55→60 FPS の改善はわずか **1.5ms** で足りる
- 実務上の意味: 「あと5 FPS 上げたい」という要求は、低FPS帯と高FPS帯で必要な最適化労力が全く違う。**budget もチェックも常に ms 単位で行うべき**という結論 [00:44–00:52]

## ベンチマーク設定：ターゲットハードウェア・解像度・frame time を固定 [01:12–01:57]

- プロデューサー陣（Jakob, Viktor）と協議し、**ターゲットハード仕様・解像度・frame time を先に決める** [01:12–01:20]
- Medieval Game Environment の実際の設定: **1080p・RTX 2080・33 FPS（≒30ms）を「安定して」出せること** [01:26–01:36]
- 制作当時（work-from-home 期）は RTX 2080 がほぼトップスペックだった、という当時の文脈込みの数値 [01:49–01:55]。※本プロジェクトへ数値をそのまま転用する意味はない（ターゲット機材が違う）
- **重要な運用判断**：本来のターゲットは 30 FPS/33.33ms ちょうどだが、**あえてそれより少し厳しい基準（33 FPS/30ms）を「performance target」として設定** [01:36–01:49]。理由は動的要素（パーティクル等のスパイク）に対する**バッファ**を持たせるため。ターゲット値と「実際にチェックする基準値」を分けるという考え方 [01:41–01:46]

## 計測の再現性を担保する仕組み：PerfCam + 自動テストBlueprint [02:11–06:52]

環境系プロジェクト（動的ゲームプレイ要素が少ない）特有のアプローチとして、**固定視点カメラ×自動化Blueprintで「毎回寸分違わぬ条件」を作る**。

### PerfCam の設置 [02:16–03:00]
- レベル内の要所（プレイヤー導線を近似する角度）に**約10台の固定カメラを配置** [02:43–02:52]。実際に使うテストBlueprintには**8台**と言及 [05:43–05:49]（=採用時に絞り込んだ可能性）
- パフォーマンス関連の仕組みは**専用サブレベルに分離**して管理 [02:19–02:22]
- 各カメラに **Actor タグ `PerfCam`** を付与 [02:22–02:25]。**Component タブでなく Actor タブの Actor tag に設定する**ことが重要という念押し（Component tag の方が Details パネルで目に付きやすく間違えやすい、との注意）[02:37–02:43]
- カメラ選定基準：**あえてパフォーマンス的に厳しいアングル**を選ぶ。例として「集落からツリーラインを振り返る」ショットは**見通し線が長く、描画物量とシャドウコストが両方重い**ため意図的に採用 [02:53–03:07]

### なぜ固定カメラが必須か [03:11–03:40]
- 手動でカメラを動かして同じ場所を見ているつもりでも、**わずかな視点のズレが「見えているものの量」を変え、apples-to-apples 比較を破壊する** [03:19–03:37]
- 実演として「同じ場所のつもりで戻ったが視点が微妙にズレ、以前は描画していなかった領域まで描画対象になっていた」という失敗例を明示 [03:35–03:40]
- → **A/Bテストの前提として「視点固定」は必須**という教訓。人力での再現に頼らない

### 自動テストBlueprintの構造 [03:40–05:38]
- BeginPlay で `Get All Actors with Tag` により PerfCam を収集 [04:00–04:03]
- `Get All Actors with Tag` は**決定的な順序を返さない**ため、**Actor 名の末尾数字でソートする自前関数**を実装 [04:05–04:14]。理由：計測データとスクリーンショットの順序を一致させ、後で work-in-progress の比較GIF等を作りやすくするため [04:14–04:25]
- 主要関数群：`StartPerf` / `EndPerf` / `DoPerfTest` / `SetCam` / `NextCam` / `BriefCam` [04:32–04:36]
- **For ループでなく再帰で処理する設計判断** [04:47–04:56]：各カメラのテストには `Delay` ノードが挟まるため、**For ループ内の Delay は期待通りに動かない**という UE Blueprint の既知の制約を回避するため
- 各カメラでの実処理手順 [04:59–05:29]：
  1. プレイヤーの View Target を現在のカメラに切り替え
  2. コンソールコマンド **`trace.start`** を実行 → Unreal Insights が GPU/CPU タイミングデータ収集を開始
  3. **約2秒間**データ収集
  4. コンソールコマンド **`trace.stop`** を実行
  5. スクリーンショットを撮影
  6. ログにカメラ完了を出力
  7. 約1秒 Delay してから次のカメラへ
  - `trace.start` / `trace.stop` は **Unreal Insights 用に UE 4.26 で新規追加**されたコマンドと明言 [05:18–05:22]
  - 全カメラ完了後は `EndPerf` を呼び、View Target をプレイヤーに戻し `Stat FPS` オーバーレイを OFF [05:32–05:38]
- `StartPerf` 自体は内部変数リセット→`Stat FPS` を ON →`DoPerfTest`（Advanced Flag = True）を発火するだけの薄いエントリポイント [04:38–04:47]

### 実際のテスト運用フロー [05:43–06:20]
1. **ビルドをパッケージ化し、エディタを閉じてからパッケージ版を起動**（=エディタ実行ではなく実機相当のビルドで計測）[05:51–05:55]
2. フルスクリーンで Play [05:55–05:59]
3. `~`（チルダキー）でコンソールを開き、**`ke * startperf`** と入力 [06:01–06:09]
   - `ke *` は「全 Blueprint をループし、カスタムイベント `startperf` を呼べるものは呼ぶ」という意味 [06:09–06:15]。該当 Blueprint はサブレベルに1つしかないため、確実に1回だけ起動される [06:15–06:19]
4. 画面右の `Stat FPS` ティッカーを見ながら経過を確認できる [06:23–06:27]
5. 診断補助として **`ke * setcam <番号>`** で任意の PerfCam へ即座に視点移動できる（テストは走らせず視点移動のみ）。**Stat GPU / Profile GPU / RenderDoc** 等の詳細診断ツールと組み合わせて使う、という言及 [06:30–06:51]

## Unreal Insights によるデータ解析手順 [06:52–08:37]

- 最終ステップは「GPU の **Average Inclusive Time**」を確認し、**全員で共有するスプレッドシートに記録**すること [06:56–07:06]
- Unreal Insights はスタンドアロンのプロファイリングツールで、リモート記録も可能（実アプリへのパフォーマンス影響を最小化する構成）[07:06–07:20]
- 起動場所 [07:20–07:34]：
  - Epic Games Launcher 版：`Engine/Binaries/Win64` ディレクトリ
  - ソースビルド版：使用中のソースエディタから自前でビルド
- 解析手順 [07:34–08:33]：
  1. `Open File` → パッケージビルドの `Saved/Profiling` フォルダにある **`.utrace`** ファイルを開く
  2. 右側のカラムビューを右クリック →`View Column`→**`Average Inclusive Time (milliseconds)`** を表示
  3. タイミングデータ上に見える「区切り」＝カメラ間の切り替わりのギャップ。**この区切りを目印にカメラごとのタイミングを分離**する
  4. タイミングビュー上でドラッグして最初のカメラ区間をハイライト・ズームイン
  5. カラムビュー最上段の **`Unaccounted`** 値＝GPU が行った全呼び出しを包含する値を確認（例：2秒区間で約 **36ms**）[08:19–08:33]
  6. これをスプレッドシートに記録し、以降のカメラでも同様に繰り返す [08:33–08:37]
- スプレッドシートを見返すと「しばらくの間 budget を超過していた期間があった」ことが視覚的に分かる、という実例が示される [08:37–08:44]

## 「早期・頻繁な計測」の効能 [08:44–09:05]

- パフォーマンスは早期・頻繁にチェック・維持するのが良い。理由は**プロジェクト終盤にまとめて対処しようとして焦る事態を避けられる**から [08:44–08:52]
- さらに踏み込んだ理由：**後で削ることになるなら、最初から作り込みすぎない方が労力の無駄がない** [08:55–09:05]（＝早期計測は「手戻り防止」だけでなく「過剰投資の防止」でもある、という二段の論理）

## Budget の立て方：「均一コスト表」ではなく「パイチャート」 [09:10–10:14]

- 「メッシュ1個◯ms」のような**均一な交換レートは成立しない**と明言 [09:10–09:24]。フレーム描画には多数の要因が絡むため
- 代わりに提案する考え方：**「1フレームに使える時間の総量」を、機能ごとに比率で配分するパイチャート**として budget を組む [09:26–09:32]
- Medieval Game Environment での実例（3つの大きな制約要因）[09:40–10:04]：
  1. フルの time-of-day サイクル → **フルダイナミックライティング**が必須
  2. 新機能の **Volumetric Clouds** を採用 → 専用のパフォーマンスコストが発生（キャプチャや stat パネルで個別に確認できる、と言及）
  3. プロジェクトの目的自体が「Quixel アセットの品質を next-gen 品質環境で見せること」→ 品質を落とせない
- これらの価値観・制約・パフォーマンス目標を踏まえ、**shadows / lighting / base pass / volumetric clouds 等、フレーム内の主要エリアごとに「緩い budget」を設定** [10:04–10:14]
- **「ビューティコーナー」または「垂直スライス」を先に作り、そこから budget の数値を逆算する**という手法を提案 [10:14–10:23]：理想の見た目・欲しい機能を全部使った小さな一角を作り込み、そのコストを budget の基準値にする
- budget の数値は「これを超えたら対処が必要」という**シグナル（cue）**として使う、という運用 [10:23–10:28]

## 「Hard Cut を避ける」という優先順位判断 [10:32–11:20]

- 本プロジェクトの目標は**ハードカットを極力作らないこと**。Jakob/Viktor が作る**ビジュアルクオリティを維持したまま**、performance target（30ms frame @ 1920x1080 @ RTX 2080）内に収めることを目指した、と明言 [10:32–10:50]
- 実例として「最も重いカメラ」を見て、shadow projection / lighting / base pass に多くの時間を使っていることを確認した上で [10:53–10:59]、**budget と『ハードカットは最小限に』という方針を踏まえ、static mesh を単純に間引いたり dynamic shadows を一律オフにする、という短絡的対応はしない**、という判断基準を明示 [10:59–11:12]
- 続編動画（本シリーズの次回作）で「ビジュアルクオリティを犠牲にしないシンプルな工夫」を扱う予告で締める [11:12–11:20]

## まとめ 5 か条（動画終盤の要約） [12:01–12:16]

1. プロジェクトに対して**現実的かつ再現可能な performance target** を設定する
2. その target 内で、**レンダリング機能ごとの budget** を作る（不確かならビューティコーナー／垂直スライスから逆算）
3. **一貫した・再現可能な方法**でパフォーマンステストを行う
4. **早期・頻繁に**パフォーマンスデータを取り始める
5. パフォーマンスの状態を**プロジェクトの全員に共有する**（パフォーマンスは全員の責任、という一文が明示される）[12:01–12:04]

次回以降の予告：**lights/shadows のチューニング・draw call の統合・HLOD 使用・cull distance 設定**でビジュアルを犠牲にせずパフォーマンスを改善する方法 [12:08–12:16]

## SCRAP BLITZ に活かせる部分

本プロジェクトの `L_Stage01`（廃工場・廃滑走路ヤード）は Content 肥大やドローコールが今後課題になり得る、という前提での抽出。この動画自体は「具体的な軽量化テクニック」より「軽量化の意思決定プロセス」がメインなので、活用余地もそちらに寄る。

1. **frame time（ms）で語る習慣づけ** [00:39–01:10]：現状は FPS ベースで語りがちだが、今後 stat コマンドで数値を見る際は ms 換算で比較する。特に「高フレームレート帯ほど改善の価値が薄い」という感覚は、既に高FPSが出ている環境で無理に最適化する優先順位を下げる根拠になる
2. **ベルトスクロールACTの「固定カメラ計測」への応用** [02:16–03:40]：SCRAP BLITZ はカメラワークが比較的定型（横視点＋奥行き）なため、L_Stage01 内の「一番重くなりそうな地点」（例：奥行きの長い滑走路見通し、複数レイヤーの廃工場構造物が重なる地点）を PerfCam 的に固定して stat 計測する運用は転用しやすい。**視点のわずかなズレが比較を無効化する**という指摘は、目視での「なんとなく軽くなった」判断への警鐘として実用的
3. **budget をパイチャート的に配分する考え方** [09:26–09:32]：本プロジェクトは Nanite 対応 Landscape・Foliage・多数の廃材プロップ・パーティクル（爆発・延焼エフェクト等）が並走する。「メッシュ1個◯ms」という単純換算をせず、**shadows / base pass / foliage / VFX ごとに budget を大枠で決めてから物量を調整する**という発想は、L_Stage01 のプロップ密度を決める際の判断軸として使える
4. **「ビューティコーナーから budget を逆算する」手法** [10:14–10:23]：L_Stage01 でも、まず理想の密度・ディテールで作り込んだ小エリア（例：滑走路脇の廃機体クラスター1か所）を先に完成させ、そのコストを測ってから他エリアの物量上限を決める、というアプローチが直接転用できる
5. **「Hard Cut を避ける」優先順位の立て方** [10:59–11:12]：Foliage やプロップを一律間引く前に、まず何が重いのか（shadow/lighting/base pass のどれか）を切り分けてから対策する、という順序は既存ドクトリン §9-10 の「映る範囲だけ品質を上げる」を実行に移す際の**手順**として補完する
6. **パフォーマンス状態のチーム共有** [12:01–12:04]：本プロジェクトは実質ソロ制作だが、「スプレッドシートに記録し続ける」という運用は、L_Stage01 のような大型背景で今後 Content 削減作業（既に handoff メモにある Content 11GB+ 削減の実績あり）を行う際の**進捗の可視化**として応用できる（何 ms 改善したかを都度記録する）

※ 本動画にはドローコール削減の具体手法（Actor Merging, HLOD 設定値, Nanite の詳細設定等）は登場しない。これらは次回動画（本シリーズ続編）に譲られているため、別途その回を学習対象にするのが望ましい。
