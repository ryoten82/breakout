## PCG とは（Points/Procedural Node Graph/Attributes-Metadataの3概念）

PCG（Procedural Content Generation Framework）は、Unreal Engine 内でプロシージャルなコンテンツ・ツールを作るためのツールセット。テクニカルアーティスト・デザイナー・プログラマーに向けて、建物や biome 生成のようなアセットユーティリティから、ワールド全体に至るまで、あらゆる複雑さの高速・反復的なツール/コンテンツを構築する手段を提供する。

中核概念は3つ。

**1. Points（ポイント）**
3D空間内の位置を表現する基本単位。「PCGグラフにより生成される3D空間内のロケーション」であり、メッシュのスポーン時に頻繁に使われる。各ポイントは以下を保持できる。
- 変換情報（transform）
- 境界（bounds）
- 色（color）
- 密度（density）
- 傾斜（steepness）
- シード（seed）
- ユーザー定義の属性（user-defined attributes）

**2. Procedural Node Graph（手続き型ノードグラフ）**
PCG の中核を成す要素で、マテリアルエディタに類似した形式で機能する。レベル内の PCG コンポーネントから空間データがグラフへ流入し、一連のノードを通じてポイントがフィルタリング・変更され、リアルタイムで出力が更新される。生成されたポイントは様々なアセットのスポーンに使われる。

**3. Attributes（属性）と Metadata（メタデータ）**
属性は変数に類似し、名前と型によってデータを保存する。静的属性（`$Position` のように `$` で始まる）と動的属性（実行時に作成されメタデータの一部として保存される）の2種がある。

## ノードカテゴリ一覧（16種）

原文で列挙されているノードカテゴリは以下の16種。個別ノードの詳細（Node Reference）は今回未取得のため、カテゴリ名のみ列挙する。

## Attributes の静的/動的区分・3つのMetadataドメイン

**静的属性 vs 動的属性**
- 静的属性: `$Position` のように `$` プレフィックスを持つ。あらかじめ定義された属性と推測されるが、原文に「定義済み属性の一覧」は無い
- 動的属性: 実行時に作成され、メタデータの一部として保存される

**Metadataの3ドメイン**
- Data ドメイン: データ自体に設定された単一値の属性用。`@Data` プレフィックス
- Points ドメイン: `@Points` プレフィックス
- Elements ドメイン: 属性セット用。`@Elements` プレフィックス

属性セレクタにより、静的属性と動的属性間の相互運用性が提供され、特定のノードで利用可能な属性の一覧が表示される、との記載がある。

※ 各ドメインが具体的にどう使い分けられるか（例: Points ドメインの属性がどのノードで読み書きされるか）の実例は原文に無く、今回のソースからは不明。

## 既存 set dressing ドクトリンとの関係（自動化できそうな点・できなさそうな点）

`bg_technique_doctrine.md` §5-8 の set dressing 原則、および出典の `wNMHF3jGXtw_construction-site.md`（工事現場動画）の各教訓と、PCG の概念を照らし合わせる。**以下はまだ実証していない推測であり、断定はできない。**

### 自動化できる可能性がありそうな点

- **decal 3種の汚し（漏水シミ・埃堆積・路面ライン）**: 工事現場動画の教訓7では decal 配置に Surface Snapping を多用し、コンクリート面などに散布していた。PCG の Points が持つ `density`（密度）属性と Filter ノードカテゴリを使えば、法線方向や地面属性でフィルタしつつ大量の decal ポイントを自動生成できる可能性がある。ただし PCG の decal 専用ノードの有無・具体的な使い方は原文に記載が無いため未確認
- **整列崩し（小さな回転で人工感を消す）**: 工事現場動画の教訓2「小さな回転を加えて他の leading line と完全に平行にならないようにする」は、PCG の Point Ops カテゴリ（ポイントの transform を変換する操作と推測される）と `seed` 属性によるランダム化で自動化しやすい部類に見える。PCG の各 Point は seed を持つため、ランダムシードに基づく回転バリエーションの一括付与は PCG の設計思想と親和性が高そうに見える
- **地形の傾斜（steepness）に応じたアセット配置のフィルタリング**: Points が `steepness`（傾斜）属性を持つと明記されているため、急斜面には配置しない・平地にのみ瓦礫を散布するといった条件分岐は PCG の Filter ノードで実現できる可能性が高い。これは工事現場動画の「地面の高さ変化（Displace ツール）」と組み合わせた瓦礫・砂山の自動散布に応用できそうに見える
- **バリエーション量産（Packed Level Actor の分解→改変→再パッケージ）**: 工事現場動画の教訓4は手作業でのプレハブ改変だが、PCG の Subgraph・Spawner カテゴリで同種の「テンプレートを大量にばら撒きつつ個体差を出す」処理を自動化できる可能性がある。ただし原文に Packed Level Actor と PCG の連携についての直接の言及は無い

### 自動化に向かなそうな点

- **anchor連鎖（大物→関連小物への「物語」の連鎖、例: 重機→資材→工具）**: 工事現場動画の教訓2「アンカーポイントからストーリーを広げる」は、「セメント袋を置いたら、それに呼応してセメントミキサーを足す」という**人間が物語的な文脈を読んで次の一手を決める**判断であり、PCG の Filter/Density のような数値条件によるフィルタリングとは性質が異なる。PCG の Attributes/Metadata の仕組みを使えば「このポイントの近くに別カテゴリのアセットを追加配置する」というルールの定式化自体は可能かもしれないが、「工具は重機の隣に置くと自然に見える」という**意味的な関連性の判断**は、原文で説明されている属性（density/steepness/color/seed等の数値的性質）だけでは表現しづらいと考えられる
- **寄り掛かり配置（セメント袋同士をもたれ掛けさせ、作業員が置いたであろう姿を想像する）**: これも「物理的にもっともらしい支え合い」という美的・物理的判断であり、PCG が扱う「ポイントの位置・変換・属性」の枠組みで簡単に再現できるかは不明。ポイント同士の相対位置関係を評価するロジックが必要になるはずだが、原文にそのような機能への言及は無い
- **構造物を「視線止め（barrier）」「leading line」として機能させる配置**: これは画面構図・カメラアングルとの関係で決まる高度に文脈依存な判断であり、PCG が個々のポイントに付与する density/steepness/color 等の属性だけでは表現が難しい部類と考えられる
- **行き詰まったら別エリアに切り替える、といった制作プロセス上の判断**: そもそも PCG が扱う領域（空間データの生成・フィルタ・変換）の外側にある人間の作業進行の話であり、対応する概念は原文に無い

**まとめ**: PCG は「数値化できる空間属性（位置・密度・傾斜・色・シード）に基づく大量散布・フィルタリング・バリエーション付与」を自動化する技術に見える。一方 set dressing ドクトリンの核心である「物語的な連鎖」「意味的な関連づけ」「構図判断」は、PCG が明示している属性の枠組みだけでは代替が難しく、**人間が最終判断する余地を残した「下ごしらえの自動化」としての活用が現実的ではないか**、という仮説にとどまる。この整理は今回の Overview 一本の情報のみに基づく推測であり、実際に PCG グラフを組んで検証したものではない。

## SCRAP BLITZ に活かせる部分

- 現在 UE 移行済みの本プロジェクトで、廃工場・廃滑走路ヤードなどの背景ステージ制作において、瓦礫・decal・小物の大量散布フェーズ（`bg_technique_doctrine.md` の decal 3種汚し等）を PCG で下ごしらえし、その後 anchor連鎖のような文脈判断が要る部分だけ手作業で仕上げる、という**ハイブリッド運用**が候補になりうる
- ただし本ノートの時点では PCG の実際のノード操作（Filter の具体的な条件式、Point Ops の変換種別、Spawner のアセット選択ロジック等）が未取得のため、実装に踏み込む前に Node Reference 系の子ページを追加取得する必要がある
- 現時点でこれを新規タスク化するかは判断材料が不足しているため保留（Overview だけでは実装方針を確定できない）
