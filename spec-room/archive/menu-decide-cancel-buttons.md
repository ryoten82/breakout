# メニューの決定・キャンセルボタン設計

## 背景・きっかけ

ユーザー発言：

> メニューなどの決定、キャンセルボタンをどうするか。
> ここ意外と大事なので時間作って考えたい。
> アーケードゲーム思考で考えるとJで決定とかになるんだけど、
> キーボードでもパッドでも位置が悪すぎる。
> どうしたもんか

「J で決定」の発想はベルスク・アーケード筐体の文脈では自然だが、現代の家庭用パッド + キーボードでは**位置が悪く**メニュー操作のテンポを損なう。
仕様書には戦闘キーバインドは §22 / KEY_CONFIG で定義されているが、**メニュー操作のキー配置は未定義**。

## 現状の入力割り当て（実装済み）

**キーボード**

| キー | 役割 |
|---|---|
| WASD | 移動 |
| Space | ジャンプ |
| J | 弱攻撃 |
| K | 強攻撃 |
| L | セカンダリ（ガード等） |
| U / I | メガクラ / ULT |

**ゲームパッド（PAD_BUTTON_MAP）**

| ボタン | 役割 |
|---|---|
| A | ジャンプ |
| X | J（弱攻撃） |
| Y | K（強攻撃） |
| L1 | L（セカンダリ） |
| R1 / R2 | メガクラ / ULT |
| D-pad / LS | 移動 |

## 論点

1. 戦闘ボタン（J）= 決定 にするか、業界標準（A ボタン / Enter）= 決定 にするか
2. キャンセルキー（B 系 / Esc）の割り当て
3. メニュー画面で戦闘ボタンを「無効化」するか「別役割で生かす」か
4. ゲームパッドの A ボタンは戦闘でジャンプ → メニューで決定、と**役割が場面で切り替わる**ことの違和感の有無
5. PlayStation 配置（×/○ 文化差）への対応

## 案

### 案A: 戦闘ボタン統一（アーケード式・J で決定）

すべての画面で J（X ボタン）= 決定。

**メリット**
- ベルスク・アーケードのお作法に従う統一感
- 「攻撃ボタンで進める」直感

**デメリット**
- ユーザー指摘の通り、**キーボード J / パッド X の物理位置がメニュー操作向きでない**
  - キーボード J: ホームポジションから少し右下・指の腹で押しづらい
  - パッド X（Xbox 配置）: 左寄り・親指の自然位置から外れる
- キャンセルボタンの直感的対応が無い（K でキャンセル？違和感）
- 業界標準と違うので、初プレイのユーザーが迷う

### 案B: 業界標準（パッド A = 決定 / キーボード Enter = 決定）

メニュー画面では **A ボタン = 決定 / B ボタン = キャンセル**（Xbox・Nintendo 標準）、キーボードでは **Enter = 決定 / Esc = キャンセル**。

**メリット**
- 全世界の家庭用ゲーム慣例に完全準拠 → 説明不要
- パッドの親指自然位置（A）で押せる
- キャンセル（B）の物理位置も自然
- キーボード Enter / Esc も PC ゲーム慣例通り
- **ジャンプ＝A＝決定** は意味的に矛盾するが、場面切り替えなので実害なし（Mario からスマブラまで多くのゲームがこれ）

**デメリット**
- 戦闘とメニューでボタンの「意味」が変わる（ただしほぼ全ゲームがこれなので問題化しにくい）
- アーケード筐体配置を再現したい場合に方針と合わない（SCRAP BLITZ は家庭機・PC 中心）

### 案C: 両方受け付ける（戦闘ボタンでも標準ボタンでも決定可）

メニューで J（X）でも Enter でも A でも決定できる。キャンセルは Esc / B / L など複数受付。

**メリット**
- 古参アーケード勢にも、家庭機勢にも対応
- どのボタンで決定できるか試して見つかる「許容範囲の広さ」

**デメリット**
- どのボタンを推奨表示するか UI ヒント設計が複雑（「Press [J] or [Enter]」のような表示は野暮）
- 「J でも決定できると思ったら、別画面では決定できない」等の一貫性事故リスク

### 案D: コンテキスト別マッピング + UI ヒント明示

メニュー = A / Enter のみ。戦闘 = J/K/L のみ。完全分離。
UI 側に「[A] 決定 / [B] キャンセル」「[Enter] 決定 / [Esc] キャンセル」を毎画面表示。

**メリット**
- 一貫性が最大
- 何のキーを押せばいいか画面で常時わかる
- 案B にヒント明示を足した形

**デメリット**
- 画面下に常時ヒント表示するスペースが必要（HUD レイアウトに影響）
- スマートな見た目が欲しい時に「[A] 決定」表示が野暮になりがち

## トレードオフ・整合性チェック

| 観点 | 案A | 案B | 案C | 案D |
|---|---|---|---|---|
| 物理的に押しやすい | × | ◎ | ○ | ◎ |
| 業界標準準拠 | × | ◎ | △ | ◎ |
| 初プレイ迷いにくさ | △ | ○ | × | ◎ |
| 学習コスト | 低（戦闘と同じ） | 低（家庭機慣例） | 高（曖昧） | 低（毎画面表示） |
| HUD への侵食 | 0 | 小 | 中 | 中〜大 |
| 北極星1（ノイズ最小化）整合 | △ | ○ | × | ○ |

**整合性チェック**
- 北極星1「ノイズ最小化」: 案C が一番ノイズ多い（曖昧さは認知負荷）
- 16:9 固定 HUD（§22）: 案D の常時ヒント表示にスペース確保が必要
- 既存 KEY_CONFIG / PAD_BUTTON_MAP: 案B/D は新規にメニュー専用マッピング追加で対応可

## PlayStation 配置の文化差（補足論点）

- **日本配置**: ○ = 決定 / × = キャンセル
- **北米・欧州配置**: × = 決定 / ○ = キャンセル
- SCRAP BLITZ がリリース地域を分けるか・統一するかで対応が変わる

**現実的な落としどころ**:
- 物理位置で考える: 「下ボタン（× / A）= 決定」を全地域共通にする方が最近の主流（PS5 標準も×統一に切り替わった）
- → **下ボタン = 決定**で統一すれば PlayStation 文化差問題は回避できる

## 現時点の傾き（叩き台）

**案B（業界標準）を推奨叩き台。** ただし**メニュー画面に控えめなボタンヒント表示**を入れて案D に寄せる。

理由：
- 物理的な押しやすさを最優先するなら家庭機標準が圧倒的に楽
- 「ジャンプボタンで決定」の意味的違和感は、ほぼ全ゲームがやっていることなので学習済みのプレイヤーがほとんど
- アーケード再現にこだわらない（SCRAP BLITZ は家庭機・PC 中心）
- キャンセルキー（B / Esc）も物理位置で自然
- 戦闘ボタン（J/K/L）はメニュー中は無効化 or 別役割（並べ替え・タブ切替等）に振り直せる

**ボタンヒント表示の方針**:
- メニュー画面下部に小さく「[A] 決定 / [B] キャンセル」（パッド検出時）または「[Enter] 決定 / [Esc] キャンセル」（キーボード時）
- 入力デバイスを自動検出して表示を切り替える（既存 Gamepad API ポーリングが流用可）
- 派手にしない（北極星1・ノイズ最小化）

## メニュー中の戦闘ボタン活用（派生アイデア）

戦闘ボタンを完全無効化せず、メニュー内の補助操作に当てる：

| ボタン | 戦闘での役割 | メニューでの提案役割 |
|---|---|---|
| J（X） | 弱攻撃 | 詳細表示・アイテム比較 |
| K（Y） | 強攻撃 | 並べ替え・絞り込み |
| L（L1） | セカンダリ | フィルタ切替・タブ移動 |
| L2 / R2 | （戦闘で SP 系） | カテゴリタブ切替（前/次） |

これは決定後・別トピックで詰めても良い（案B が決定するなら）。

## 決定（2026-05-14）

- **採用案**: **案B 寄り（業界標準準拠）+ ボタンヒント表示**で確定
- **決定キー**: **下ボタン**（Xbox: A / PS: ×）/ キーボード Enter（or Space）
- **キャンセルキー**: **右ボタン**（Xbox: B / PS: ○）/ キーボード Esc
- **PS 文化差**: 「下ボタン = 決定」物理位置統一で吸収（PS5 標準も下統一済み）
- **追加方針（ユーザー発案）**: **アクション操作とメニュー操作でキーコンフィグを分離**
  - `KEY_CONFIG` を `ACTION_KEY_CONFIG` と `MENU_KEY_CONFIG` の 2 系統に分割
  - 設定画面で「アクションキー」「メニューキー」の 2 タブに整理 → ユーザーフレンドリー
  - 戦闘の J を変更してもメニュー操作には影響しない（事故防止）
- **採用理由（要約）**:
  - キーボード J / パッド X は物理位置がメニュー操作向きでない
  - 業界標準（A=決定 / B=キャンセル / Enter=決定 / Esc=キャンセル）は説明不要・初プレイ迷いゼロ
  - 戦闘 ↔ メニューのボタン意味切替はマリオ〜スマブラ慣例で学習済み
- **保留・後続トピック化**:
  - 戦闘ボタン（J/K/L）のメニュー内活用（詳細表示・並べ替え等の補助役割）→ メニュー実装着手時に別トピック化
  - リバインド UI の実装時期・タイミングは別途検討
- **反映先**: 仕様書本体 §22.5 として新設（§22.5.1〜§22.5.4 構成）
- **ユーザー判断の経緯**:
  - 「アーケード思考で J 決定だが位置が悪い」→ 案A 却下
  - 「B 寄りでいきたい・決定は PS × ボタン」→ 案B 採用 + 下ボタン統一
  - 「アクションとメニュー操作を分離した形でキーコンフィグできるとユーザーフレンドリー」→ 系統分離を追加採用
