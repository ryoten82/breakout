# ターミナル「歩ける拠点」化案（宇宙公園跡地）

## 背景・きっかけ

ユーザー構想：

> ターミナルは移動できる拠点みたいなものを考えている。
> 例えば古い宇宙公園跡地、的なもの。
> 奥に朽ち果てた巨大パラボラアンテナが並んでいて、
> そこに各々がスクラップで作った拠点を用意しており、
> ショップだったり強化ポイントだったりにアクセスできる、とか。
>
> 単純に動けるメニューは楽しいし、
> マルチとかで何となくみんなでバタバタ動き回るのも楽しいのではないか、という想像。

仕様書本体の現状記載：
- §5: 「ターミナル＝4人の**地下拠点**（メカ修理・チップ装備・出撃地点）」
- §13.2: ショップ機能の詳細（チップガチャ・スロット拡張・OC解放・恒久強化・ストック補充・上限突破）
- §15: ボス撃破でターミナル機能が段階解放
- §11 Phase 4 ゲート: 「ターミナル画面が触りたくなるか」

→ **「地下拠点」**設定と新案「**宇宙公園跡地（地表ロケーション）**」が衝突。
→ **メニュー画面**前提だった UI を **歩ける物理空間**に拡張する案。

## 論点

1. ロケーション再定義：「地下拠点」→「宇宙公園跡地」に書き換えるか（§5 の上書き）
2. インタラクション形式：歩ける空間 / 純粋メニュー / ハイブリッド（歩ける空間 + 各拠点で従来 UI が開く）
3. マルチプレイ時の挙動（バタバタ動き回る体験の演出）
4. 実装規模：簡素なフラット床 + ファサード vs 凝ったロケーション
5. 出撃動線：歩いて出撃ゲートへ向かう / メニューから即出撃

## 案

### 案A: フル歩行型ターミナル

各キャラの拠点が地表に並び、プレイヤーは自由に歩いてアクセス。
- 動線: 出撃ゲート / METEO 拠点 / VIPER 拠点 / BASTION 拠点 / CANNON 拠点 / 中央広場 / ショップ
- 各拠点に近づくと「装備」「ショップ」「強化」等のインタラクトプロンプト表示

**メリット**
- 「動けるメニューは楽しい」を最大限享受
- マルチで散歩・集合のバタバタ感が一番出る
- ロケーション自体が世界観を語る（パラボラ群 = 主人公達の置かれた状況の示唆）
- Phase 4 ゲート「触りたくなるか」を最も満たしやすい

**デメリット**
- 実装コスト**大**：3D 空間制作・カメラ・歩行 AI（NPC キャラ表示）・インタラクト UI・場所記憶
- 出撃までの動線が長くなる（テンポ低下）→ ショートカット（ホットキー/メニュー併用）必須
- 戦闘画面と別カメラ・別物理系が必要

### 案B: ハイブリッド（歩ける空間 + 拠点ごとに既存メニュー）

地表は歩ける（演出重視）が、拠点に入る = 従来のメニュー画面が開く。
ベルスク本編と同じ操作系で歩き、メニュー操作だけ既存 UI を再利用。

**メリット**
- メニュー UI 資産（§13.2 ショップ等）を完全再利用
- ロケーション演出と機能 UI の責務分離 → 実装が段階的に進められる
- 出撃動線は「中央広場の出撃ゲート」に直行で短縮可

**デメリット**
- 歩く時間 = 純粋な演出時間なので「触りたくなるか」の評価は案A 未満
- 拠点入退場で画面遷移が入る（テンポ要注意）

### 案C: メニュー画面のまま、背景にロケーションを描く

実装は従来のメニュー画面方式を維持。背景イラスト/3D 静止画として宇宙公園跡地を見せる。

**メリット**
- 実装コスト**極小**：背景差し替えだけ
- 世界観（パラボラ群・スクラップ感）は十分伝わる
- テンポは最高（メニューだから即座にアクセス）

**デメリット**
- 「動けるメニュー」の楽しさは得られない
- マルチのバタバタ感はゼロ
- §5 の「地下拠点」を変えるだけで案C は成立してしまう（新規性が薄い）

### 案D: 案A の段階実装（C → B → A）

- Phase 4: まず案C（背景イラスト化）で世界観を整える
- Phase 5: 案B にアップグレード（歩ける空間 + 拠点ごと既存メニュー）
- 余力次第で案A まで踏み込む（住民 NPC・イベント等）

**メリット**
- 早い段階で世界観の片鱗を出せる
- 完成度を段階的に上げられる
- 案A のリスク（テンポ低下）を実プレイで検証してから次段階へ進める

**デメリット**
- 「動けるターミナル」の楽しさを早期に検証できない
- 中途半端で止まる可能性（C で固定化してしまう）

## トレードオフ・整合性チェック

| 観点 | 案A | 案B | 案C | 案D |
|---|---|---|---|---|
| 「触りたくなるか」（Phase 4 ゲート） | ◎ | ○ | △ | C→B 進行で改善 |
| 実装コスト | 大 | 中 | 極小 | 段階分散 |
| マルチのバタバタ感 | ◎ | ○ | × | 段階で開花 |
| テンポ（出撃までの早さ） | △ | ○ | ◎ | 段階で調整 |
| 既存 UI 資産活用 | △ | ◎ | ◎ | ◎ |

**整合性チェック**
- 北極星1（手触り重視・ノイズ最小化）: 案A は出撃テンポ悪化のリスク。案B/D が穏当
- §5「地下拠点」記述: いずれの案でも上書きが必要（→「宇宙公園跡地」に再定義）
- §13.2 ショップ仕様: 案B/C/D では既存 UI 再利用可。案A は新 UI 必要
- §11 Phase 4 ゲート: 案A〜D で達成度に差。案D の進行管理が無難
- マルチ前提構造との整合: 既に `players[]` 配列対応・案A〜D いずれも追加負担なし

## 実装観点メモ

- **メカで歩く違和感**: ベルスク本編と同じメカで街中をうろつく絵面が成立するか？
  - 案: ターミナル内は搭乗解除（パイロット人型で歩く）/ そのままメカ歩行 / どちらでも切替
  - パイロット人型を出す場合、4 キャラ分のキャラモデルが追加で必要（コスト増）
- **NPC（住人）の有無**: 「宇宙公園跡地」にどの程度の生活感を出すか
  - 完全廃墟 vs 細々と住人がいる で世界観が変わる
  - ストーリー §5 の「OVERLORD 侵略」設定と整合する範囲で決める
- **マルチ時のバタバタ感**: 案A/B では他プレイヤーキャラが同居して見える設計が前提
  - 傭兵モード（archive/mercenary-mode.md）との連動可能性 → 単独プレイ時に AI 仲間がターミナルでも動いていれば「賑やかさ」演出になる

## 現時点の傾き（叩き台）

**案D（段階実装：C → B →（必要なら A））を推奨叩き台。**

理由：
- 「動けるメニュー楽しい」「マルチでバタバタ動き回る楽しさ」というユーザー期待は案A が最大化するが、実装コスト・テンポ低下リスクが大きい
- ターミナルは**戦闘の合間に頻繁に訪れる場所**なので、テンポ悪化は手触り重視（北極星1）と直接衝突する
- 段階実装なら世界観の早期確立（案C）と将来の歩ける体験（案B/A）を両立できる
- 案B で止まっても十分楽しい（既存ベルスクの拠点表現として標準的）

なお、設定書き換え（地下 → 宇宙公園跡地）は案によらず即座に §5 を更新する価値がある。
ロケーションの絵が固まること自体が、UI 意匠やドロップ演出にも波及する。

## 決定（2026-05-14）

- **採用案**: **案D（段階実装：C → B → A）**
- **ロケーション**: 「宇宙公園跡地・朽ちたパラボラアンテナ群・各自のスクラップ拠点」を**仮置き**として §5 に反映。ただし**ストーリー次第で変動する前提**なので、設定詳細を強く書き込みすぎない（実装が拘束されない範囲で）
- **実装方針**: 簡単なものから順に。最初は背景イラスト/簡素 3D 静止画（案C）でロケーション感を出す。歩行体験は後段（案B）で追加
- **派生論点の決定**:
  - **メカで動く**（搭乗解除なし・パイロット人型キャラモデルは作らない）。ターミナル全体の**スケールを大きめに取って**メカが歩いても違和感ない絵作りにする
  - **NPC 配置**: 優先度低。ゲーム本体（戦闘・チップ・OC）を厚くするのが先。余裕が生まれてから検討
  - **傭兵モードの仲間**: ターミナル内では動かさない。やりすぎ禁止。仲間 AI はあくまで戦闘中に動く存在
- **採用理由（要約）**:
  - ロケーション設定はストーリー確定で変わりうるため、実装を凝りすぎない方が手戻りリスク低
  - ターミナルはテンポ重視（戦闘の合間に頻繁に訪れる場所）→ 案A の歩行動線長期化リスクを段階的に検証
  - ゲーム本体の磨き込み優先方針と整合
- **反映先**:
  - §5 ストーリー・世界観: ロケーションを「地下拠点」→「宇宙公園跡地（仮置き）」に更新、メカで歩く・スケール大きめ方針を明記
  - §13 章: 「ターミナル形式・段階実装」セクション新設（案D の C/B/A 段階定義と各 Phase での達成基準）
  - §11 Phase 4 ゲート: 「ターミナル画面が触りたくなるか」を案C ベース（背景イラスト＋既存メニュー UI）で評価する旨明記
  - 傭兵モード archive: ターミナル内で AI 仲間を動かさない方針を追記
