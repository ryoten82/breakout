# 背景・ステージ構築ワークフロー

## 背景・きっかけ

ユーザー発言：

> 背景をどうするかほとんど考えてなかった。
> マップチップみたいなものを配置するモードとか考えてたけど、
> 簡単に言うとマリオメーカーみたいなやつね。
> 他にアイデアある？

仕様書本体の現状記載：
- §26: 「背景は Synty POLYGON Sci-Fi 系購入 + 3DSMax で部分手直し」（**アセット調達方針のみ**）
- §11 Phase 6: 「パララックス・スモーク・遠景・霧などで奥行き」（**ポリッシュ要素のみ**）
- §1.5: `bgCamera` でパース付き背景描画・ステージ範囲は X クランプ済

→ **ステージをどう構築するか（ワークフロー・データ形式・ツール）は完全に未定義**。
→ ユーザー案「マリオメーカー型エディタ」を含めて選択肢を並べる必要がある。

## 論点

1. ステージ構築の主体（誰が何で組むか）
2. データ形式（コード直書き / JSON 等のデータ駆動 / エディタ専用バイナリ）
3. UGC（ユーザー作成ステージ）を視野に入れるか
4. プロシージャル要素の有無（北極星4 と要整合）
5. Three.js プロト段階のステージ表現と、Unreal 移行後の制作環境をどう橋渡しするか

## 案

### 案A: マップチップ／プロップ配置エディタ（ユーザー案・マリオメーカー型）

GUI で部品（地形・建造物・破壊オブジェクト・敵スポーン点）をグリッドや自由位置に配置するエディタを自作する。

**メリット**
- ユーザー（アニメーター本職）の感覚で「並べる楽しさ」を取り込める
- データ駆動なので、後で MOD・UGC 共有に発展可能（Steam Workshop 等）
- マルチで「みんなが作ったステージで遊ぶ」体験が成立する
- ステージ追加のリードタイムが極小（コード触らずに増やせる）

**デメリット**
- **エディタ自体の開発コストが大**（保存形式・UI・プレビュー・バリデーション）
- Three.js プロト段階で作っても、Unreal 移行で作り直しになるリスク
- 1作目のステージ数（3ステージ＋ボス×3 = 限定的）に対してオーバースペック気味
- UGC を視野に入れると審査・モデレーション等の運用コストも発生

### 案B: 手作りシーン（Unreal 上でデザイナーが配置）

Unreal の Level Editor で 3D 空間にプロップを直接配置。伝統的なベルスク制作の主流方式。

**メリット**
- Unreal の既存機能をフル活用（Lumen・Nanite・Niagara との統合）
- 表現の自由度が最大（カメラ動き・カットイン・スクリプテッドイベント等）
- カプコン旧作 / ベアナックル IV 等の参考作品と同方式 → 学習リソース豊富
- 1作目のステージ数なら工数は許容範囲

**デメリット**
- Three.js プロト段階で本格的なステージ表現ができない（Three.js 用に別途簡易実装が必要）
- UGC は不可（あるいは別途エディタ実装が必要）
- ステージ追加 = エンジニア＋デザイナー作業が必要

### 案C: プリセットスロット組み合わせ（ハイブリッド）

「ステージブロック」を手作りで複数用意し、組み合わせ順だけデータで定義。
例: stage1 = [opening_block, fight_arena_A, transition_corridor, mid_boss_block, ...]

**メリット**
- ブロック単位なら手作りでも数を作れる
- データ側で組み替えるだけでステージバリエーション増産可
- プロシージャル感は出せるが、ブロック自体は固定（北極星4「ランダム性は配置のみ」と整合可）
- エディタは「並び順を入れ替える」程度の簡素 UI で済む（案A より軽い）

**デメリット**
- ブロック境界の繋ぎ目が不自然になりやすい
- 「ステージ全体の演出弧」を組むのが難しい（カプコン旧作のような構成の妙が出にくい）
- 中途半端で誰得感が出るリスク（手作りでも UGC でもない）

### 案D: データ駆動 + 後付けエディタ（推奨叩き台）

ステージ構造を JSON 等のデータで定義（プロップの座標・敵スポーン点・カメラ遷移など）。
最初は手書き or 簡易ビューア。後で必要なら案A のエディタを被せる。

**メリット**
- データ駆動 → 後からエディタを被せても上位互換
- 1作目は手書き / 簡易ツールで進められる（投資を後ろ倒し）
- Unreal 移行時もデータをコンバートしやすい（汎用形式なら）
- UGC を後で開く判断もできる

**デメリット**
- 「マリオメーカー的な作る楽しさ」は最初は得られない
- データスキーマ設計が肝（一度決めるとリファクタが重い）
- ユーザーの「作る楽しさ」期待を満たすのは将来の話

### 案E: プロシージャル生成

ローグライト的にステージ要素をランダム生成。

**メリット**
- ステージ作成工数が劇的に減る
- リプレイ性が高まる

**デメリット**
- **北極星1（手触り重視・ノイズ最小化）と直接衝突**
- 北極星4「ランダム性は敵配置・OC・チップドロップのみ」に明確に反する
- → **本案は最初から不採用候補**（記録のみ）

- ユーザーの動機（作る楽しさ）: 案A が最強。案D は後付けで案A 相当に拡張可能

## 現時点の傾き（叩き台）

**案D（データ駆動 + 後付けエディタ）を推奨叩き台。** 補強として**段階的に案A の要素を取り込む**設計を提案。

理由：
- 1作目の規模（3ステージ＋ボス×3）に対して案A のフルエディタは過大投資
- データ駆動で進めれば、後で「やっぱり案A のエディタが欲しい」となった時に追加実装で対応可（互換性が保てる）
- Unreal 移行を見据えると、データ形式の汎用性（JSON 等）が橋渡しコストを下げる
- ユーザーの「マリオメーカー的な作る楽しさ」は将来の UGC 機能として温存できる（1作目クリア後のエンドコンテンツ・MOD コミュニティへの拡張）

**案A との折衷案**: データスキーマ設計の段階で「エディタが将来被せやすい構造」を意識しておく。例：プロップ ID + 座標 + 回転 + パラメータ の単純レコード形式にしておけば、エディタは GUI でこのレコードを編集するだけになる。

## ユーザー案との関係

ユーザー発案「マップチップ配置（マリオメーカー型）」= 案A 相当。これは案D の延長線上にあるので、廃案ではなく「**まずデータ駆動で土台を作り、エディタは後付けで案A 相当を実装する**」流れに統合できる。完全に案A 一本で行く判断も可。
