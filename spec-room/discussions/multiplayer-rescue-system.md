# マルチプレイ救助システム（黒化中の蘇生）

## 背景・きっかけ

Phase 2.4 で死亡演出（黒化 → 黒↔赤点滅 → 爆散 → 完全消滅 → respawning 落下）を
実装した際、ユーザーから「マルチプレイ時はこの流れの途中に救助フェーズを挟みたい」
という要望。

シングルプレイでは「dead state 1 秒待機 → 自動 respawning」だが、
マルチプレイでは別プレイヤーが介入できる救助タイミングを設ける。

## 仕様（要望ベース）

### 死亡フロー（マルチプレイ版）

1. HP 0 → dying（黒化 0.5s）
2. 黒化完了 → **黒くなったまま動かない状態 + 頭上に死亡ゲージ付与**
3. 別プレイヤーが救助動作（接触 + ボタン押しっぱなし）で救助フェーズ進行
4. 救助ゲージ満タン → **体力 10% で復帰**
5. 間に合わなければ → 黒↔赤点滅（周期加速）→ 爆散 → 完全消滅 → respawning

### 各タイミング（暫定値）

- 黒化フェード：0.5s（既存）
- **救助受付時間**：5〜8s（要調整）
- 救助動作の押下時間：1〜2s（要調整）
- 救助受付が過ぎたら：黒↔赤点滅 0.5s → 爆散
- 救助成功時の復帰 HP：MaxHP × 10%
- 救助成功時の無敵F：通常リスポーンと同じ（4 秒透明点滅）

### 救助動作

- 救助者：別プレイヤーが死亡キャラに**密着 + 救助ボタン押しっぱなし**
- ボタン：仮で L キー（セカンダリ）/ 専用ボタン追加か検討
- 救助中の救助者：その場ロック・移動不可（攻撃で割り込まれる可能性あり）

### 頭上 UI

- 死亡ゲージ（円形 or バー）：救助受付時間 → 黒↔赤点滅時間 の合計を表示
- 接触中の救助者がいる場合：別色（緑系）で救助進行ゲージを上書き表示

## 論点

1. **シングルプレイでの扱い**：単独プレイ時は救助システムを無効化（dead 即 respawning）
   - PAUSE_CONFIG.allowFullPause と同じパターン：`RESCUE_CONFIG.enabled = false` で枠切替
2. **救助動作のボタン**：既存ボタン流用 or 新規追加（メニュー操作との競合注意）
3. **救助中の救助者の無防備さ**：攻撃で中断されるか、無敵か
4. **救助回数の上限**：1 ステージ N 回まで、等の制限を入れるか
5. **死亡ペナルティとの整合性**：仕様書 §13.5 で「死亡=7割没収」とある。
   救助復帰でもペナルティ発生するか、救助は無傷か

## 案

### 案A: 完全独立救助システム（要望そのまま）

- 内容: 上記仕様をそのまま実装
- メリット: 要望に沿う・Co-op の協力感が出る
- デメリット: 実装規模大・救助 UI・別プレイヤー検出・救助動作判定・タイムアウト制御が必要

### 案B: 簡易救助（救助時間=救助動作時間）

- 内容: 死亡ゲージは無し。接触 + ボタン押下 N 秒で即復帰
- メリット: 実装最小・UI も簡素
- デメリット: タイミング感が薄い・「間に合うかどうか」のドラマが無い

### 案C: 仕様凍結・実装は Unreal 移行後

- 内容: 仕様だけ確定し、実装は Unreal 移行（マルチプレイ本実装）後
- メリット: Three.js プロト段階での実装コストゼロ・Unreal の蘇生システムと整合した実装が可能
- デメリット: 体験が確認できない

## トレードオフ・整合性チェック

- 設計の柱（北極星6原則）との整合:
  - ❻マルチ対応意識：救助システムは Co-op の核
  - ❶手触り重視：救助 / 救助される感覚の手応えが重要
- 既存仕様への影響:
  - dead state の挙動分岐（シングル即復活 vs マルチ救助待ち）
  - §13.5 死亡ペナルティとの整合（救助時の没収ルール）
- 実装コスト感:
  - 案A: 大（UI + ロジック + バランス調整）
  - 案B: 中
  - 案C: ゼロ（仕様メモのみ）

## 現時点の傾き

**案C（仕様凍結・Unreal 移行後実装）**

理由：
- Three.js プロト段階ではマルチプレイ自体が動かない
- 救助システムは Unreal の Replication と一緒に設計したほうが筋
- ただし dead state の枠（黒化のまま待機する 1 秒）は既に Phase 2.4 で確保済み
- マルチ実装時にここを「救助受付時間」として拡張するだけ
